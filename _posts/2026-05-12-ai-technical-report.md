## 💡 技术详解

### 1️⃣ vLLM v0.20.x：不只是修 Bug，更是架构升级的前奏

**痛点：** 最近几个月，社区里吐槽最多的是："为什么新出的模型（尤其是 MoE 架构和视觉语言模型）总要在 vLLM 上等兼容？"

**解法：** vLLM v0.20.2 虽然是一个 patch release（6 commits，6 contributors），但背后反映的是 vLLM 正在快速跟进多模态和 MoE 模型的趋势。本次重点修复了：
- **DeepSeek V4**：MoE 路由的推理兼容性问题
- **gpt-oss**（OpenAI 开源模型）：权重加载和注意力计算适配
- **Qwen3-VL**：视觉-语言跨模态推理的 Bug

但更重要的是，v0.20 系列已经积累了大量底层优化：
- **异步调度器（Async Scheduler）大幅改进**：请求排队延迟显著降低，高并发场景下吞吐量提升明显
- **Chunked Prefill 更加成熟**：把长 prompt 切成小块处理，避免大 prompt 阻塞整个推理流水线
- **更好的 FP8 推理支持**：在保持精度基本不降的前提下，显存占用减半

**效果：** 用 vLLM 部署 DeepSeek V4 的延迟比早期版本降低了约 15-20%。对于做 LLM 服务化的团队来说，这意味着同样的 GPU 可以扛更多的 QPS。

---

### 2️⃣ SGLang v0.6.x：RadixAttention 如何让显存"记住"一切

**痛点：** 跑过多轮对话的朋友都知道一个痛点——每轮对话都要重新计算前面已经算过的 KV Cache，GPU 的算力被白白浪费。更夸张的是，同一个 prefix（比如系统 prompt）被重复计算了几十次。

**解法：** SGLang 的核心卖点 **RadixAttention** 本质上就是给 KV Cache 建了一棵"前缀树"（trie）。简单理解：

> 就像你背课文，第一遍全文背诵；第二遍你只需要接着上次停的地方往下背，而不是从头再来。

v0.6.7 在前缀缓存（Prefix Caching）上又做了增强：
- **跨请求共享 KV Cache**：不同用户的请求，只要有共同的 prompt 前缀，就能复用已计算的 KV
- **与 Disaggregated Prefill/Decode 结合**：把 prompt 处理（prefill）和 token 生成（decode）拆到不同 GPU 上，前缀缓存在两者之间共享
- **更好的 RadixAttention 内存管理**：缓存命中率更高，eviction（淘汰）策略更智能

**效果：** 在多轮对话和 RAG 场景下，前缀缓存命中率可以达到 60-80%，相当于 **节省了同等比例的 prefill 计算量**。这对于部署在边缘或小集群上的团队来说，是实打实的成本下降。

---

### 3️⃣ Mooncake & KV Cache 分离式部署：让显存不再是瓶颈

**痛点：** 推理系统最大的性能瓶颈是什么？答案可能不是算力，而是 **显存**。KV Cache 随着上下文长度线性增长，128K 上下文下，一个请求的 KV Cache 可以占掉几十 GB 显存。

**解法：** Mooncake（以及类似思路的 KV Cache 分离式部署方案）提出了一个大胆的想法：**把 KV Cache 从推理 GPU 上搬出去，存到专门的内存服务器（CPU 大内存节点）或 RDMA 互联的显存池中**。

类比一下：
> 传统推理 = 厨师（GPU）做菜时，所有食材（KV Cache）都必须放在灶台上（GPU 显存），灶台有限，一次只能做几道菜。
> Mooncake 方案 = 灶台只放当前要用的食材，其余的放在旁边的大仓库（CPU 内存池），需要时通过传送带（RDMA）快速取用。

**效果：** 这种架构下：
- 单 GPU 能同时服务的请求数增加数倍（因为 KV 不占 GPU 显存了）
- 超长上下文（128K+）推理成为可能
- 代价是增加了 RDMA 网络延迟，但通常这个延迟远小于重新计算 KV Cache 的时间

目前 vLLM 和 SGLang 都在探索类似的 KV offload 方案，这几乎肯定是 2026 年下半年推理引擎的标配功能。

### 4️⃣ 推测解码（Speculative-Decoding）：让 LLM "猜着说"

**痛点：** LLM 推理是 **自回归** 的——每生成一个 token 都要跑一次完整的 forward pass。生成 1000 个 token 就要跑 1000 次，这就是为什么大模型输出看起来"一个字一个字蹦"。

**解法：** 推测解码的思路很巧妙：**用一个小模型（draft model）快速"猜"出接下来的几个 token，然后用大模型一次性验证**。

> 就像一个打字快的人先帮你打出草稿，你再花很少的时间检查对错。猜对了就省时间，猜错了重新来。

目前的技术进展：
- **Eagle / Medusa 等架构**：训练专门的 draft head，比用独立小模型更高效
- **vLLM 和 SGLang 都已原生支持**：配置几行代码就能启用
- **自推测解码（Self-speculative）**：同一个模型，前面几层做 draft，后面几层做 verify，连小模型都不需要

**效果：** 在代码生成等可预测性高的场景，加速比可达 **2-3x**；在对话场景也有 **1.3-1.8x** 的提升。这意味着同样的 GPU，可以服务更多的用户，或者同样的用户，可以获得更快的响应。
